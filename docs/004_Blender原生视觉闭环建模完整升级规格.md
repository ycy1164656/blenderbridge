## 1. 任务目标与不可替代的完成条件

### 1.1 最终用户流程

```text
GPT Image 生成概念／三视图 → 用户批准 → 参考图片保存到本地
          ↓
Codex 实际读取参考，登记比例、轮廓、截面、部件与未知区域
          ↓
BlenderBridge 建立冻结参考、可执行建模计划和新候选
          ↓
Blender 原生建模
  网格／曲线／截面／修改器／Geometry Nodes／局部雕刻
          ↓
固定多视图与局部出图 → Codex 实际看图 → 登记具体差异
          ↑                                      ↓
  新版本出图并检查副作用 ← 锁定保护区、执行局部修形
          ↓
达到视觉自评标准 → UV／材质／烘焙 → 绑定／动作／技术检查
          ↓
可继续编辑的 .blend + 部件／配方 + 网格／贴图 + 验收证据
          ↓
经项目授权，由 UnrealBridge 执行 UE 导入与独立验证
```

这里的“本地”指几何创建、场景编辑、渲染、网格处理、材质制作与文件产出在本机完成。Codex 的参考理解与看图审阅、GPT Image 的概念生成沿用用户当前服务，不要求离线，也不在本次任务中重做。原生建模过程中可以在授权范围内复用本地资产，必须登记来源。

### 1.2 本次必须形成的能力

| 能力 | 完成条件 |
|---|---|
| 原生视觉闭环建模 | 无额外图生 3D 模型依赖，真实完成参考理解、结构建模、固定出图、实际审阅、局部修正与再验证 |
| 可控且可编辑的几何 | 能依据轮廓、截面和结构约束建模，保留部件与关键参数，不以基本体堆叠作为最终造型 |
| 持续精修 | 指定一个部位进行修改，其他锁定部位不被破坏；有修改前后对照及保护区检查 |
| 参考匹配与差异跟踪 | 参考图与模型在可比较的尺度、姿态和相机条件下审阅，差异关联真实图片及候选版本 |
| 游戏资产处理 | 几何、拓扑、UV、材质、烘焙、骨架、权重及导出具备完整可用路径 |
| 可靠执行 | 任务与闭环阶段可查询、产物可追踪、失败不被冒充成功，检查点可恢复 |
| 真实交付 | 有真实本机闭环记录和代表性资产，而不仅是测试小样、截图接口或功能清单 |

### 1.3 明确不做什么

不接入商业图生 3D 云 API，不自动把素材上传给第三方，不建设计费和云密钥体系，不实现多用户 SaaS、云队列、账户体系或复杂网页后台，不训练基础模型，也不默认安装神经图生 3D 或学习式贴图后端。

允许复用开源算法、Blender 自带功能和已获授权的本地插件。需要增加的依赖应有明确任务收益；不要以收集插件代替打通制作链路。未安装图生 3D 模型不能成为核心建模、测试或交付的阻塞理由。

### 1.4 必须区分的状态

```text
implementation_complete   所需软件能力是否实现
local_execution_verified  原生建模闭环是否在本机真实运行
technical_validation     网格、UV、权重、导出等技术检查
visual_self_review       Codex 根据实际图片给出的视觉自评
user_visual_acceptance   用户对指定产物版本的真实批准
ue_validation            指定 UE 版本中的独立导入／运行验证
```

这些字段相互独立。模型质量不达标时，继续修改；存在真实不可消除的阻塞时，保留成果并明确阻塞，不制造“全部通过”。缺少用户最终批准不妨碍交付候选，但不得把自评写成用户批准。一次建模操作或渲染任务成功，也不等于整轮闭环完成。

## 3. 完整目标架构

### 3.1 三层职责

**Codex：**实际读取参考和模型渲染，理解形体与结构，登记部件、建模计划和视觉差异，选择并执行局部修改，记录自评。BlenderBridge 不另开一个未经授权的视觉模型 API 来代替 Codex，也不能用文件存在或单一分数冒充看图。

**BlenderBridge 主机层：**统一数据契约、操作发现、建模任务与闭环阶段、参考包和配方、产物索引、比较图合成、差异记录、检查点与本任务后台 Blender 调度。

**Blender 执行层：**以原生几何与制作能力承担核心三维建模。交互实例的 `bpy`／`bmesh` 场景操作在主线程执行；渲染、烘焙、复杂重网格等重任务可在本任务专用后台 Blender 实例中处理冻结快照。[R09][R10]

```text
Codex：看参考／看渲染／规划／记录差异／决定局部修正
  │ MCP / 同契约 CLI
  ▼
BlenderBridge Host
  ├── catalog / schema / routing
  ├── reference + asset + recipe manifests
  ├── modeling jobs + iteration state + review records
  ├── image comparison + geometry reports + artifact registry
  ├── checkpoints + owned background Blender jobs
  └── Blender session client
           │ loopback + session + revision
           ▼
      Blender Add-on
        main-thread queue → bpy / bmesh / 原生建模与制作能力
           │
           └── 固定渲染与检查结果 → 返回 Codex 实际审阅
```

默认架构不包含外部图生 3D 推理进程、模型注册中心或模型权重缓存。后台 Blender worker 用于制作计算隔离，不承担图片语义理解。

### 3.2 不能混淆的执行域

catalog 新增执行域和副作用描述，至少能区分：

```json
{
  "execution_domain": "blender_main_thread",
  "mutates_scene": true,
  "writes_artifacts": false,
  "long_running": false,
  "requires_gui": false,
  "requires_gpu": false,
  "cancellation": "queued_only"
}
```

其他核心执行域为 `host_cpu`、`isolated_blender_worker`。此结构需与旧 `mutates` 字段有清楚的兼容规则。

MCP 或 HTTP 工作线程不能直接触碰 `bpy`。耗时渲染、烘焙和重网格应根据操作能力采用后台快照或可分步任务；确需在交互主线程运行时，声明阻塞行为，不虚称异步执行。

### 3.3 闭环任务与场景任务分离

参考校准、建模计划和差异记录依赖冻结的参考包与候选版本；Host 只负责登记和验证，不能因提交了参考图片就宣称已经理解形体或建立模型。

每批场景修改必须使用当前 session／revision、精确目标与保护区。后台任务先取得指定候选的输入快照和哈希，完成后返回产物；若要将结果应用到交互场景，另行核对当前对象版本并显式执行。

源网格已经变化时，后台结果保留为产物，不自动覆盖新网格。旧版本图片不能关闭新版本差异；一次成功的后台任务不自动推进到“视觉通过”。

### 3.4 本地连接保护保持简洁

保留 loopback 和会话令牌，这是防止误连其他 Blender 或误写当前工程的本地安全机制，不是第三方服务 API 密钥。无需用户管理云账户，不建设计费系统。

无需增加大规模鉴权平台；输入输出根、进程身份、写入范围、版本保护和恢复功能不可因“自用”而删除。

## 4. Blender 原生视觉闭环建模核心

### 4.1 核心定位与职责

Blender 是本方案的核心三维几何生成、编辑和制作执行引擎。Codex 负责根据图片推断建模意图并审阅结果；BlenderBridge 将这些决策转为有范围、有版本保护、可查询和可恢复的 Blender 操作。

“原生”指几何与制作通过 Blender 的数据结构、网格／曲线工具、修改器、Geometry Nodes、雕刻、材质和烘焙能力完成。允许在 Bridge 中封装轮廓、放样、选择和局部变形算法，不把原生限定为人工点击，也不要求每个部件都使用同一种技术。[R09][R10]

把图片放入场景只建立了参考；理解结构、建立几何、识别差异与修正仍须分别实现。核心目标不是一次性执行长脚本，而是让模型在实际视觉反馈下持续变得更符合批准参考。

### 4.2 必须跑通的制作闭环

1. **读取参考：**查看实际图片，登记视角、姿态、比例、轮廓、关键点、已批准范围及未知结构。
2. **拆解与计划：**划分胸甲、肩甲、关节等语义部件，选择网格、截面、曲线、修改器或雕刻方法，声明本批目标、参数和保护区。
3. **原生建模：**在新候选中创建或修改真实几何，保留部件身份、可编辑参数及制作记录。
4. **固定出图：**按冻结相机和显示条件输出灰模、线框、部件图与必要的局部图，记录候选和图片版本。
5. **实际审阅：**Codex 打开图片，与参考逐项比较，记录主要差异及受影响部件，不能用渲染成功代替审阅。
6. **局部修正：**优先修比例、主平面、厚度、连接和负空间，锁定无需改变的部位，再执行精确操作。
7. **再验证：**重新出图，检查目标差异是否改善、保护区是否保持及其他视角是否出现新问题，决定继续修正或进入技术整理。

常规迭代在当前授权范围内自主进行；用户要求审核的节点遵从用户指示。重大参考矛盾应标明，不通过擅改批准设计来制造通过。

### 4.3 原生能力与可选扩展边界

| 能力 | 本次定位 |
|---|---|
| 网格／曲线／截面放样／扫掠 | 核心几何创建路径，覆盖实际机械与装甲结构 |
| 修改器／参数化配方／Geometry Nodes | 支持可控更新和复用；选用与部件相符的方法，暴露并验证实际使用的参数 |
| 局部选择／雕刻／重网格／重拓扑 | 支持有保护区的精修和后续游戏网格整理 |
| 固定渲染／比较图／差异单／再次修正 | 整个 BlenderBridge 的核心闭环，必须真实执行 |
| UV／投射／材质节点／烘焙／绑定／导出 | 将已审阅造型整理为可编辑、可交付资产 |
| 其他图生 3D 或学习式贴图工具 | 非默认、非必需；仅在另行明确选用时接入，不作为核心安装、测试或完成条件 |

本次不要求安装任何图生 3D 模型，不下载模型权重，不建设对应推理 worker。缺少这些扩展不得标为核心功能阻塞，也不得用扩展输出替代原生闭环验收。已有相关代码或环境不自动删除，其状态在现场盘点中如实记录。

### 4.4 资源与质量要求

实际查询 Blender、CPU、GPU、显存、RAM 和磁盘。资源要求来自所选建模、渲染、烘焙及几何规模，不能套用图生 3D 模型的显存门槛。

逐步测量代表资产的编辑延迟、渲染／烘焙时间及峰值资源。预览可以使用经过验证的显示模式、CPU／GPU 路径和分辨率档位，但最终检查必须能辨认关键结构，不以降低画质掩盖问题。

资源不足时保存成果、保留真实失败，并继续不受影响的范围；不关闭用户程序、不自动转云。使用 Blender 原生能力也不自动证明美术达标，完成条件始终由真实参考对比、可编辑结构和交付验证决定。

## 5. 安装、能力探测与本机运行

### 5.1 Host 与 Blender 环境

复用现有 Blender 插件及 Host 环境。确需增加参考图处理、比较图合成或任务存储依赖时，安装到隔离的 Host 环境；Blender 侧使用其实际支持的 Python／API，不向插件环境塞入无关依赖。

不默认安装 PyTorch、CUDA 工具链或图生 3D 模型环境，不改变现有 Codex、UnrealBridge、全局 Python 或其他项目环境。安装脚本先输出精确改动计划，检测并复用兼容资源，备份本任务修改的原有配置。

Windows 为当前目标环境。原生建模核心不以 WSL 为前提；不得擅自升级驱动、启用系统功能、重启电脑或终止 UE 腾显存。

### 5.2 实现本机诊断

目标命令：

```powershell
blender-bridge doctor --json
blender-bridge capabilities --json
blender-bridge verify --suite native-modeling --run-fixture
```

诊断至少输出 Blender 身份与 API 版本、Host 解释器、实际可用的网格／修改器／雕刻／渲染／烘焙／导入导出能力、图像返回通道、GPU／显存、可用 RAM／磁盘、必要依赖及本任务后台 Blender 状态。

应区分：`available`、`verified`、`missing_dependency`、`unsupported_capability`、`unsupported_device`、`insufficient_resources`、`failed_probe`。只有实际运行过的能力才能设为 `verified`；测试场景能运行不等于实际视觉闭环或用户美术验收已经完成。

核心诊断不探测或要求图生 3D 模型权重。自动验证套件可检查几何、渲染和版本保护；实际看图及差异判断由 Codex 按 A-01 完成并单独记录。

### 5.3 原生算法与依赖来源

优先使用 Blender 自带能力和已授权插件；新增算法、节点组、配方及 Host 依赖保存来源、版本、哈希和必要许可。各依赖单独记录，不把整个依赖链统称 MIT。

不把外部模型下载或第三方推理密钥设为安装前提。不支持的 Blender 操作应明确报告真实缺口，选择可验证的原生实现或登记阻塞，不能用示例网格填补空实现。

### 5.4 真实本地运行证明

至少一次完整原生建模闭环记录：Blender／Host 版本、session／revision、参考哈希、建模计划、实际操作与部件参数、前后几何、固定渲染、Codex 实际审阅和差异单、修正结果、保护区检查与产物哈希。

后台 Blender 任务另记 PID、启动命令、输入快照、输出哈希、日志、峰值资源与耗时。证明核心流程没有调用图生 3D 后端：在未配置相关后端的环境中执行，并保留实际路由、进程与依赖清单。

无需断开工作站网络影响 Codex／GPT Image；配置开关不能当作任意 Python 已被完全网络隔离的证明。真实建模与审阅不得用假网格、缓存示例或未打开的图片冒充。

## 6. 参考图、三视图与图像交接

### 6.1 GPT Image 交接边界

本次不新增 GPT Image API 账户或密钥。复用用户当前能使用的图片生成方式；Bridge 接收保存到本地的图片、相应需求与批准记录。

有图片生成工具的 Codex 环境可在已有授权中准备图；没有该能力的执行环境应生成明确的参考图请求文件，并正确登记待补视图。不能宣称 Bridge 可通过当前不存在的工具直接画图。

生成新候选图、读取旧批准图、批准参考图是三件不同的事。未经批准的新图不能替换已批准标准。

### 6.2 参考包功能

实现图片登记、接触表、明确矩形裁切、蒙版修正、尺度／基线校准、关键点登记、方向标注、冻结与版本比较。

原始图片只读保留。裁切、去背景、旋转、填充都产生派生文件并记录变换。通过明确裁切框拆分三视图，不默认三张视图等宽；不使用 OCR 作为主路径。

三视图可有重复尺寸标线、文字和底色，应从用于轮廓分析、视觉比较和纹理投射的派生区域移除；有用的尺寸标注另行登记。必须检查主体未被裁断、透明边缘正确、武器／角／披挂／细杆没有误删。

### 6.3 视角、尺度与姿态

建立 `view_label`、`camera_convention`、`pose_id`、`subject_bbox`、`ground_line`、`center_line`、关键点和实际世界高度。缺少实际高度时保留 `unknown`，可用归一化建模单位工作，不编造最终厘米尺寸。

“左视图”统一指角色自身左侧，不是观察者画面左侧；参考相机、Blender 场景和导出格式的约定显式转换。使用带不对称标识的校准件验证方向，不允许靠镜像碰巧过图。

像素坐标统一为左上角原点，X 向右，Y 向下；记录像素尺寸和像素中心约定。正交缩放保持像素等比，不用横纵独立缩放掩盖比例误差。

默认采用明确的建模坐标约定：`+Z up`，资产正面朝 `-Y`；角色自身左侧在该约定下为 `+X`。这只是本项目内部约定，不假定导入格式与 UE 坐标一致；跨坐标系转换写入矩阵并用校准件验证。

### 6.4 参考一致性检查

比较头、肩、胸、腰、髋、膝、脚底等关键高度；机械资产比较底座、旋转轴、主要外壳与武器轴线。报告显著的视角冲突、姿态冲突和不可见区域。

多个外观图并不能唯一决定隐藏几何。明确区分 `observed`、`inferred`、`user_specified`；用户已批准正面时，不能为了让背面容易建模偷偷改变正面。

只有正面时可以继续局部和可见区域制作，但不得把猜测背面标为已批准三视图。多视图对齐、建模与审阅闭环的系统测试可使用单独的合成校准件，不因此冒充项目资产已有全视图批准。

### 6.5 图像返回能力

扩展现有图像读取工具，让它能够读取已登记的参考图和对比图，而不仅是运行时渲染 PNG。检查允许目录、文件类型、尺寸与哈希；返回实际 MCP 图像内容，不仅返回文件名。

生成的对比图带 `reference_revision`、`candidate_revision`、相机和渲染设置摘要。图像被修改或对应模型过期时，拒绝拿旧图作为当前证据。

### 7.3 部件与网格身份

对象使用持久 `bb_object_id`，网格数据使用独立 `bb_mesh_id`，部件使用稳定 `part_id`。名称仅用于可读展示，不做唯一身份依据。

复制对象时生成新 ID 并记录来源；链接副本的网格身份与独立副本不同；合并、拆分、应用修改器后更新映射。载入其他 `.blend` 或恢复检查点后，session 必须按原有语义失效更新。[R02]

边、面、顶点选择绑定 `topology_revision`。拓扑改变后，旧索引失效；无法明确重映射时返回 `STALE_SELECTION`，不能依靠“顶点数量没变”判断索引一定有效。

### 7.4 制作步骤与可修改参数

`recipe.json` 记录实际建模步骤及可编辑参数，例如胸甲截面、肩宽、装甲厚度、倒角范围、镜像平面、部件父子关系。

重放使用逻辑 ID 映射到本次对象，不照抄旧对象名和旧面编号。记录 Blender／算法版本及实际参数；使用程序化随机变化时另记种子，不保证跨版本逐字节一致。对已修改工程重放应先检查前置条件并创建新候选，不覆盖用户手工修正。

### 7.5 资产要求与技术预算

从 ShooterRoyal 已有规范读取单位、命名、三角形预算、材质槽、纹理尺寸、骨架、动画和 LOD 要求。未定义的字段保留未知并在交付报告单列。

允许设置用于本次验证的明确测试档，但不得把自拟数字写成用户原有要求。资源预算是游戏运行要求，不是云调用费用上限。

## 8. 原生建模任务与闭环状态

### 8.1 建模计划与请求契约

核心接口围绕 `modeling.plan`、`modeling.submit`、`modeling.inspect`、`modeling.resume` 组织。计划由 Codex 在实际读取参考后形成；`modeling.plan` 负责登记和校验，不能把文件路径自动变成未经审阅的建模判断。

请求至少包含 `job_id`、`asset_id`、冻结参考包及哈希、候选 ID／revision、当前 session／scene revision、部件与操作清单、配方参数、保护区、固定相机集和本地输出目录。新建候选时先分配身份；已有候选必须核对版本。

操作清单只引用 catalog 中实际可用的能力，并声明会创建／修改哪些对象、是否改变拓扑和是否保存。提交前检查输入、能力、范围与资源；未实现的动作返回结构化错误，不返回成功空壳。

这些操作名均为待实现目标，与现有分组 MCP 和 job 查询整合，不并排创建另一套场景协议。

### 8.2 从参考到可执行几何

读取校准后的独立图片，记录实际查看过的产物、视角与参考版本。先形成轮廓、截面、主平面、厚度、部件连接及不可见结构的建模假设，再选择对应 Blender 操作。

建立有效透明蒙版时，先检查图像内容；仅把 RGB 转成 RGBA 不等于背景已被移除。缺失视角不复制正面充数；只用单视角时明确约束范围和推断区域。

参考像素、建模坐标和相机之间使用有记录的映射。不能把未经校准的轮廓直接挤出并称为精确复原，也不能从参考中不存在的尺寸编造最终世界单位。

### 8.3 候选与中间产物

创建几何的请求必须产生真实非空网格，验证顶点／面有限、包围盒合理、方向和单位明确；编辑请求另行报告实际变化及保护区结果。结果示例：

```json
{
  "workflow": "blender_native_visual_loop",
  "asset_id": "fixture_mech",
  "candidate_revision": 2,
  "iteration_id": "iteration_002",
  "reference_views_used": ["front", "left", "back"],
  "modeling_phase": "awaiting_visual_review",
  "artifact_role": "editable_candidate",
  "blend_artifact_id": "fixture-editable-blend",
  "recipe_artifact_id": "fixture-recipe",
  "render_artifact_ids": ["fixture-front-r2", "fixture-left-r2", "fixture-back-r2"],
  "protected_parts_check": "passed",
  "visual_status": "not_reviewed"
}
```

这只是字段示例，不是已产生的真实证据。另附实际操作日志、对象／部件映射、参数、资源测量、坐标矩阵和输入输出哈希。候选必须能继续编辑，不能只返回预览图或不可追踪的网格文件。

`editable_candidate` 和子任务 `succeeded` 都不表示美术完成；`visual_status` 只能依据对应候选的实际审阅更新。

### 8.4 闭环推进与暂停点

建模闭环使用独立阶段，例如：

```text
planned → editing → awaiting_visual_review
                           ↓ 实际看图并记录差异
                        revising → editing
                           ↓ 差异复核及视觉自评满足要求
              ready_for_technical_validation
```

具体作业运行状态仍遵循第 16 节。阶段为 `awaiting_visual_review` 时，由 Codex 打开当前图片、调用 `review.record` 登记观察和后续操作，再通过 `modeling.resume` 继续；Host 不能因图片存在就自行关闭差异或假装已经审阅。

恢复时核对参考、候选、图片、相机和当前场景版本。版本变化后重新出图或重做受影响的计划，不重用失效判断。等待 Codex 审阅不等于每轮都要求用户确认；只有用户要求的审核节点和真实新增授权范围才等待用户。

达到视觉自评标准后才进入正式材质、绑定与交付整理。后续操作若改变轮廓、结构或观感，重新打开受影响的审阅项；用户最终批准仍是独立状态。

### 8.5 候选、局部重建与导入

原生创建默认进入本任务新候选 collection。一次保留少量有明确目的的候选，以差异驱动修改，不无限重做整件模型。优先调整部件参数或局部几何；确需重建部件时，在独立候选中创建，声明连接面、枢轴、尺寸和替换范围。

局部修复必须验证非目标部件与保护区保持。整件模型重新生成、用旧候选替换或改变相机掩盖差异，均不能算局部修复。

复用已授权资产时，源文件只读保留，导入进入新候选并建立独立可编辑对象；报告对象映射、网格统计、纹理依赖和初始固定视图。尺度与方向通过显式变换校准，发现格式差异时保留诊断件，不靠随手缩放截图制造一致。

## 9. Blender 对象与修改器操作补齐

### 9.1 导入／追加

至少支持实际可用的 GLB／glTF、OBJ、FBX，以及从 `.blend` 追加指定对象／集合。核实本机导入器是否可用，并把格式能力加入 catalog。

检查外部纹理依赖和相对路径；禁止打开任意 `.blend` 替换当前用户场景作为普通“导入”。追加与打开文件应是不同操作。

每次导入报告新增数据块、命名冲突处理、父子关系、材质和贴图路径。默认不删除同名对象，不污染原有候选。

### 9.2 基础对象操作

实现对象和集合的创建、复制、独立化、重命名、移动、显隐、父子关系、原点／枢轴、合并、分离与精确删除。

删除提供精确目标预览并受当前 revision 保护。按模式查找可以返回预览，但不能不展开对象列表就执行大范围删除。

`object.transform` 明确 local／world 空间，应用变换分别控制位置、旋转、缩放，不能请求“只应用缩放”却把位置也烘入。旋转角单位、欧拉顺序／四元数必须声明。

### 9.3 修改器完整管理

在已有 add／apply 基础上，补 inspect、update、remove、reorder、copy。[R02]

覆盖真实制作所需的 Bevel、Mirror、Solidify、Subdivision、Boolean、Weighted Normal，以及 Shrinkwrap、Decimate、Remesh、Triangulate、Array、Simple Deform 等经过本机验证的参数子集。

每个类型采用独立参数 schema。至少能控制镜像轴和参考对象、合并／裁切、倒角限制和段数、布尔操作及操作数、厚度偏移、细分显示与渲染级别。具体 RNA 属性按安装版本查询，禁用无效字段。

应用修改器前保存检查点，并声明是否改变拓扑／UV／权重。批量应用不能默认包含 Armature 或破坏现有绑定。

### 9.4 基础与最终网格分别检查

提供 `mesh.inspect(mode="base")` 和 `mode="evaluated"`。基础网格用于编辑；最终网格用于检查修改器计算结果、当前姿态和导出前状态。

实现 evaluated depsgraph 读取和临时网格释放；不能把临时 evaluated mesh 留在场景或用于假稳定索引。返回当前帧、depsgraph 上下文、修改器摘要和数据来源，区分两套统计。

检查面数、零面积、松散几何、边界、法线、连通块、包围盒、UV、材质槽。自交检测允许分级：粗筛与精确检查必须区分；预算不足或未运行时返回 `not_checked`，不能默认为 0。

## 10. 语义部件、选择与局部修形

### 10.1 部件登记和来源

实现 `part.register`、`part.inspect`、`part.lock`、`part.unlock`、`part.assign_region`。部件可以对应独立对象、一个对象上的区域，或一组对象。

初始语义由 Codex 根据参考和场景登记。支持按连通块、材质、空间、法线聚类提出分区建议，但“自动按连通块分离”不能被命名为已理解“肩甲／关节”。

为分件结果标记来源 `explicit`／`geometric_proposal`／`reviewed`。边界不明确时先显示有颜色的区域图，确认后再做破坏性分离。

### 10.2 选择查询

至少支持：对象／部件 ID、包围盒／球／高度区间、法线方向和夹角、材质区域、连接区域、边界／尖锐边、顶点组／遮罩、射线拾取。

复杂选择可以组合交集、并集、排除和扩展／收缩。查询结果带命中数量、包围盒、选择 ID、对象和拓扑版本，可输出选择叠加图；默认不传输整张高模的所有顶点。

### 10.3 从屏幕反馈到网格位置

`selection.pick` 接收具体图像产物／相机、像素坐标或矩形、多对象范围与可见性策略；使用与该图相同的投影和深度建立 ray cast。

必须处理裁切、缩放、图片 Y 方向、透视／正交差异、遮挡和背面。参考图上的像素并不天然等于模型顶点；参考图拾取先经过已登记的对齐映射，再在对应模型视图中确认。

射线命中 evaluated 面时，不能直接用该面编号去修改基础网格。能映射则验证映射；不能映射则转为世界空间局部选择或要求显式基础网格操作。

### 10.4 局部修改工具

实现选择范围内的移动、旋转、缩放、沿法线偏移、带渐变的抓取、平滑、平面化、截面缩放、轮廓贴合与对称修正。

每项声明影响空间、半径、falloff、强度、迭代次数、遮罩和保护区。默认保留其他部件。对于左右不对称设计，不默认对称化。

受限局部位移可采用明确的渐变函数，例如余弦衰减：

```text
w(d) = 0.5 × (1 + cos(π × d / radius)),  0 ≤ d ≤ radius
w(d) = 0,                              d > radius
p_new = p_old + w(d) × mask_weight × delta
```

这是可复现的局部变形，不应冒称等同于 Blender 所有原生雕刻笔刷。

### 10.5 修改不外溢的验证

在局部修改前后检查锁定对象和保护区域。拓扑未变时比较世界空间坐标及必要的法线／材质状态；拓扑变化时使用部件映射、表面距离和独立哈希检查，不用旧顶点编号直接比较。

如果原本只能保护对象而不能保护对象内部区域，必须如实报告，不要对混在同一网格中的“头部”宣称锁定成功。

## 11. 硬表面、雕刻与重拓扑

### 11.1 硬表面建模必须具备可控轮廓

补齐闭合轮廓生成、曲线／路径、截面放样、沿路径扫掠、壳体厚度、边环桥接、支撑线、切割、边滑移、面分离和受限倒角。

截面放样至少验证顶点顺序、起点对齐、法线方向、截面扭转、封口和自交；不要求支持所有任意 CAD 曲面，但要覆盖装甲、炮管、底座和连接件的实际样例。

一块复杂胸甲应能用多个截面的形状与厚度控制，并保留继续编辑的参数。需要真实体积的缝隙、装甲层和凹槽不能只画在颜色贴图上。

### 11.2 原生几何路线的范围

实现 `geometry.profile`、`geometry.loft`、`geometry.sweep` 或等价操作。可把多视图轮廓相交体作为粗模辅助，但必须标记 `blockout`：轮廓没有告诉系统的凹陷和隐藏连接仍需设计／修改。

多视图轮廓交集只提供形体约束，不能替代装甲主平面、凹陷、厚度和连接的制作与审阅。采用 Geometry Nodes 时登记节点组来源、版本、输入参数和 evaluated 结果；采用直接网格算法时保留配方。两种实现都要能在局部修改后重新检查几何与图片。

### 11.3 适合 Agent 的雕刻支持

提供可在明确三维坐标上执行的 Grab／Smooth／Inflate／Flatten 类局部操作、遮罩、对称与有限重网格。优先使用可测试的几何运算，不依赖不稳定的鼠标坐标回放。

若暴露 Blender 原生雕刻笔刷，必须声明 GUI／模式要求、创建正确上下文、验证笔刷资产／版本行为、恢复原上下文；运行测试应与几何模拟笔刷分开。

多分辨率与体素重网格分别记录对 UV、权重、形状键和拓扑的影响。禁止在已绑定的生产对象上无检查地执行破坏性重网格。

### 11.4 高模／低模／工作模型分开

明确 `native_source`、`high_detail`、`editable_work`、`game_low` 的角色；复用外部网格时另记只读来源角色。某些资产可以角色共用一个网格，但必须是明确选择，不能一份高密度网格从头用到底又称“已优化”。

重拓扑至少有两类可用路径：

- 静态／刚性部件：受控减面或经验证的 QuadriFlow 等本地重网格，保护轮廓和分件边界。
- 需要连续变形的区域：条带／边环生成、贴合高模、关节区域局部整理和形变测试。

自动四边化不保证合格的动画布线；禁止把“四边面比例高”作为关节可用的唯一证据。对于机甲，优先考虑刚性部件独立骨骼驱动，柔性连接单独处理。

### 11.5 复用和批量变体

保存已验证装甲、连接件、塔底座等局部模板及参数。支持按 recipe 生成尺寸／造型变体，重放后仍需检查。

不得在首件未达到要求时批量复制成整套塔和机甲。一次完整升级要求实现批量功能，不等于要求未经首件验证就批量制作生产资产。

## 12. 固定多视图与视觉反馈闭环

### 12.1 标准预览集

至少支持 front／left／back、另侧辅助视图、三分之四主视角、指定局部特写和转台。相机由参考包和资产尺寸确定，不能每轮重新自动裁切到不同比例。

灰模、轮廓、法线、线框、材质、部件 ID／选择遮罩分别出图。用固定渲染配置验证材质；工作预览可调分辨率，最终图要能辨认关键结构。

纯灰模图不能被辅助立方体、其他候选、参考图片平面或隐藏的旧对象遮挡。每张图记录精确对象集合。

### 12.2 比较图与图像证据

`compare.views` 产出参考／当前并排、轮廓叠加、关键点差异、局部放大和改前／改后对照。图片边缘标注版本和视角，内容区不加遮挡关键结构的文字。

`compare.region` 返回指定结构而非每次都重传全图。对照图由本地图片处理产生，不让图像生成模型重绘模型渲染，以免丢失真实几何证据。

必须使用 MCP 图像返回或 Codex 当前可用图片查看工具实际查看。文件存在、渲染成功、图片哈希正确只能证明产物产生，不能证明视觉已审阅。

### 12.3 辅助度量

可以计算固定对齐下的轮廓 IoU、关键点归一化误差、轮廓距离和已配对表面的几何偏差。对齐只允许有记录的相机／尺度修正，不允许非刚性拉伸把不合格比例强行配准。

指标不是单一美术分数。默认输出原始值和差异图；门槛来自已冻结的资产 profile 或实验校准，不把随意的“90 分”作为用户批准。

参考未标注姿态／关键点或并非正交时，相关指标返回 `not_applicable`／`uncertain`，不要产生假的精确数值。

### 12.4 差异单驱动下一次操作

每轮审阅关联实际打开的图片 ID／哈希、参考 revision、候选 revision、相机集和迭代 ID，并写入结构化差异：

```json
{
  "issue_id": "shoulder_profile_001",
  "part_id": "left_shoulder_shell",
  "views": ["front", "left"],
  "category": "silhouette",
  "severity": "major",
  "observation": "肩甲外缘过宽，侧面前后厚度不足",
  "proposed_action": "局部收窄外缘并调整侧向截面",
  "protected_parts": ["head", "torso_core"],
  "status": "open"
}
```

以上是测试示例，不是对现有模型的实际观察。真实差异必须指向刚刚查看的图片版本。

修改后关闭差异项需要对应新图、实际复核和保护区结果，不能只因为执行了 `mesh.edit` 就自动关闭。`review.record` 只登记 Codex 的实际观察；Host 不把轮廓指标、文件生成或计划文本自动转换为视觉自评通过。

### 12.5 自评与批准

优先修比例、轮廓、厚度、机械连接、负空间，再修材质和细节。黑缝不能替代厚度，磨损不能掩盖大形错误。

当多轮操作没有降低主要差异时，改变实现路线：局部重做、切换截面结构、选择更合适候选或修正存在矛盾的参考。记录为什么变化，不无限增加小零件。

用户要求中途审核时按其要求等待；未要求逐步审核则自主完成授权范围内的迭代。只有用户对指定版本的明确接受，才能写入 `user_visual_acceptance=approved`。

## 13. UV、贴图、PBR 与烘焙

### 13.1 UV 不是只调用 Smart Project

在现有基础展开能力上，补接缝标记、按部件展开、UV 岛检查与重排、纹素密度、旋转／缩放、padding 和重叠检查。[R02]

允许有意镜像复用 UV，但必须登记。需要不对称涂装、独立烘焙或运行时绘制的区域不能误用镜像重叠。纹理分辨率与纹素密度来自资产 profile，不按整个项目一刀切。

UV 修改后使旧烘焙失效；网格或 UV 改变时，不保留“贴图仍已验证”的状态。

### 13.2 本地贴图制作路径

必须提供“已有参考／本地纹理 → 多视图投射或材质语义 → UV 贴图 → Blender 材质”的完整实现。

支持的 PBR 通道至少包括 BaseColor、Normal、Roughness、Metallic、AO、Emissive 和需要时的 Opacity。没有数据的通道可使用明确的材质常量，但不能把常量假称为推断出的贴图。

默认采用 Blender 原生材质节点、已授权本地纹理、参考投射、纹理绘制和高低模烘焙完成贴图。程序化材质按交付需要烘焙，不要求学习式贴图模型。额外纹理工具仅按第 4.3 节作为可选扩展；不能为了贴图更换已经审阅的几何。

### 13.3 多视图投射

投射依据已登记相机、可见性和深度；避免把正面颜色投到背面、把手臂颜色投到躯干、把被遮挡区域当作可见。

实现视角权重融合、接缝处理和覆盖率报告。缺失区域标记为未覆盖，可采用语义材质／局部修补，不凭空把一个正面投射称为完整 360° 贴图。

颜色参考可能含高光和阴影；投射到 BaseColor 前应识别风险，允许使用中性光参考、局部去光照或受控手工／程序化修补。不能把烘在颜色中的强光当作真正 PBR 材质。

### 13.4 高低模烘焙

实现显式 high／low 配对、烘焙笼、射线距离、目标 UV、纹理分辨率、边缘扩展和通道输出。禁止依赖当前随手选择状态决定烘焙对象。

Normal、AO 及所需材质通道分别生成；材质烘焙与光照烘焙的用途区分。按匹配部件隔离烘焙或使用已验证的防串扰措施，避免肩甲法线烘到脖子上。

记录 Blender 版本、渲染引擎、切线基准、几何三角化策略、UV 哈希和法线方向约定。导出低模的三角化、法线和切线策略须与烘焙一致。

失败、空白图、全常量异常和明显投射穿透要有诊断图。烘焙文件存在不是成功的唯一条件。

### 13.5 材质节点和引擎交接

增加材质查询、更新、复制和贴图重链接。以 Principled PBR 可导出的参数集为主；复杂 Blender 程序化节点需要烘焙到目标贴图，不能假定 FBX 会保留任意节点网络。

BaseColor 等颜色图与 Roughness／Metallic／AO／Normal 等数据图设置正确的色彩空间。通道打包使用显式 swizzle 清单；不把 ORM 排列默认为整个 ShooterRoyal 唯一约定。

对于 Blender／glTF 与 UE 法线约定差异，记录是否翻转绿色通道或由导入配置完成；只能做一次，不能在导出和导入同时翻转。

发光区域独立检查，灰模验收通过前不使用强发光掩盖几何缺陷。输出材质球／目标资产的固定光照预览。

## 14. 绑定、权重与动画验证

### 14.1 绑定只在造型可接受之后用于交付

完整升级需要实现绑定功能，但代表资产不能跳过视觉检查直接做动作来证明“有进展”。

同时支持：机械刚性部件绑定、一般骨架创建和调整、已授权骨架复用、权重编辑／转移／归一、自动权重作为初始候选、动作采样与形变检查。

Rigify 或 UE to Rigify 的模板思路可用于本地骨架映射，但需核实已安装版本和具体骨架兼容性。不能把“能生成 Rigify”当作自动兼容 Paragon 或 UE 目标骨架。[R08]

### 14.2 骨架数据

骨骼检查包含父子层级、rest pose、roll／轴向、长度、deform 标记和根骨。保留骨架模板及 rest-pose 哈希。

机械部件优先使用明确枢轴和刚性权重；柔性连接才使用连续蒙皮。骨架映射不只比较名称，还要检查姿态、尺度和旋转基准。

### 14.3 权重修正

补齐清除／修改／平滑／镜像／归一／限制影响数／从源网格转移。只统计实际 deform bones 的权重，不把任意用户顶点组当作骨骼权重。

归一化前检查未权重顶点。自动补权重必须记录规则和范围；不能随意把所有未绑定顶点分配到 root 后宣布通过。

权重转移应指定空间、最大距离与部件限制，避免左右肢体或重叠装甲串权。

### 14.4 动作与形变证据

至少验证 neutral、抬臂、屈肘、转躯干、屈膝或与该资产相符的机械动作，以及回到原姿态。

检查穿插、关节间隙、权重泄漏、异常伸缩、骨骼／物体变换叠加、rest pose 恢复和导出动作范围。对刚性肩甲，抬臂不能把装甲拉成橡皮。

输出对应固定视角图片和采样数据。单一“出拳”动作只证明该动作的某些状态，不代表全部关节合格。

## 15. 游戏资产整理与 UE 交接

### 15.1 打包前校验

校验基础／最终几何、单位、轴向、枢轴、贴地位置、命名、材质槽、纹理路径、UV、权重、骨架、动画范围、LOD 和碰撞。

开放壳体、双面薄片等可以合法存在；以资产用途判断边界，不设置所有模型“非流形边必须为 0”的僵硬规则。

碰撞单独产出简单形状或符合资产要求的凸体集合，不把复杂视觉高模默认作为碰撞。LOD 不能只看减面比例，还要在目标视距检查轮廓、材质和形变。

### 15.2 导出清单

输出 `.blend`、选定中间格式／FBX、需要的 GLB 检查文件、独立贴图和清单。明确源高模、可编辑工作模型、游戏网格的角色，不让用户只能得到不可继续修正的单一三角网格。

清单包含资产 ID／revision、源 blend 哈希、精确对象列表、世界尺寸、骨架、导出配置、帧范围、贴图通道和色彩空间、检查结果、参考与视觉审阅状态。

选定交付目录中纹理必须能解析；不能靠用户电脑上某个意外绝对路径才能显示。可打包入 `.blend`，同时按项目需要输出可供 UE 使用的独立纹理。

### 15.3 独立读回

使用本任务新建的独立 Blender 进程重读源文件和导出物；验证尺寸、方向、网格、UV、材质依赖、骨架、权重与动作。

Blender 内部 FBX roundtrip 不能替代 UE 导入。记录原始导出和各导入器的坐标／帧偏移，避免通过互相抵消的转换制造假通过。

### 15.4 UnrealBridge 交接

BlenderBridge 实现 `export.prepare_ue` 产物清单和只读可检查的导入计划；不复制 UnrealBridge 的 UE 场景控制实现。

在明确授权的路径和资产范围内，由已有 UnrealBridge 执行导入／保存／冷读／预览。无授权或 UE 不在可用状态时，交付可用资产和计划，标记 `ue_validation=not_run`；不把整个工具升级假装成 UE 已通过。

可参考 Send to Unreal 的导出设置模板、资产识别与批量交付思路，但是否复用其代码／插件由实际版本兼容性决定。[R07]

## 16. 任务、恢复与执行可靠性

### 16.1 任务持久化

保留现有 request_id 去重机制，为原生建模批次、视觉闭环和后台 Blender 长任务增加持久化记录。可使用 SQLite，单机自用无需分布式队列。

建议状态：

```text
queued → running → succeeded
                 → failed
                 → cancelled
                 → interrupted
                 → result_unknown
```

阻塞信息可用独立 `blocked_reason`，如必要原生能力不可用、资源不足、参考缺失或输入版本冲突。未安装图生 3D 模型不构成阻塞。超时不等于失败；断线后查询原任务，不自动换 ID 再执行。

一条父制作任务可以有子任务，但必须记录具体执行域、输入版本、每个子任务结果与已产生的副作用，并持久化第 8.4 节的闭环阶段和待审阅证据。父任务不能因为最后一个截图成功就掩盖未审阅状态或之前失败的导出。

### 16.2 并发与资源

默认同一 Blender session 串行写入，同一 GPU 同时执行一个本任务重渲染／烘焙作业。后台几何、渲染与烘焙根据实际 RAM／显存预算调度，不能无协调地耗尽工作站资源。

可以释放本任务临时 evaluated mesh、渲染缓存及已完成的自有后台实例；不能关闭用户的 UE／Blender 或其他程序。OOM 后按已验证档位调整批次、预览设置或 CPU／GPU 执行路径并明确记录，不能无限重试、掩盖质量下降或自动转云。

### 16.3 取消语义

普通正在执行的 Blender `bpy` 操作不宣称支持安全强制中断。排队操作可取消；能提供协作取消的 worker 在安全点停止。

本任务拥有的后台 Blender 进程可以在身份核实后终止；已运行到什么程度、是否留下半成品必须明确。部分产物写临时文件，完成并校验后原子重命名为正式产物。

不得按进程名批量结束 Blender／Python。验证 PID、启动时间、命令和本任务身份。

### 16.4 检查点与恢复

实现 `checkpoint.create`、`checkpoint.list`、`checkpoint.restore`。保存模型、参数、引用和产物清单；恢复不是只复制一个 `.blend` 文件名。

默认恢复到新候选／独立实例，保留当前现场。确需替换当前场景时必须有明确操作语义、当前未保存状态处理和完整恢复点。

恢复后验证对象／网格身份、重新建立 session 和 revision、使旧选择与审阅失效。外部导出文件不会被 Blender undo 自动恢复，必须在清单中明确处理。

### 16.5 批量写入不假装原子事务

增加带预检查和写入范围的 batch。要么采用隔离副本成功后显式替换，要么报告部分执行。仅有 undo push 并不等于可以对文件、后台烘焙、导出和场景跨域原子回滚。

### 16.6 Python 兜底

保留已有显式启用的 `python.execute`，但不把核心功能隐藏在长脚本里。常用算法沉淀为测试过的受控操作或 recipe。

任意 Python 是受信任的非沙箱执行，其权限限制不能虚假宣传。即使启用，也必须遵守当前工程授权、精确对象范围和检查点要求。[R02]

## 19. 建模 Skill 与自主修正策略

### 19.1 更新现有两个 Skill

`blender-bridge` 负责准确会话、实时 catalog、执行域、自有后台 Blender、建模任务与阶段查询、图片读取、恢复和安装态诊断。

`blender-reference-modeling` 以原生视觉闭环为主流程，负责实际读取参考、结构拆解、原生建模方法选择、分件与修改、实际看图、差异单和技术／美术验收。补充原生操作及配方的短小参考，不复制整套规则形成漂移。

### 19.2 必须遵守的循环

```text
实际打开当前批准参考，读取资产要求
→ 检查原生能力、已有候选、现场与授权
→ 拆解比例／轮廓／截面／部件，登记未知结构
→ 选择原生操作或已授权资产复用，登记可执行计划
→ 在精确范围创建／修改可编辑几何并保留配方
→ 输出固定多视图，实际打开并与参考比较
→ 记录关联版本的主要差异和保护区
→ 执行有目的的局部修正
→ 再出同角度图，实际复核改善与副作用
→ 重复至视觉自评满足要求，再完成技术整理和交付
```

这里“满足自评”不是由系统一次截图自动打分。Codex 必须记录看到了什么、改了什么、哪些差异仍未解决。中断后先读取闭环阶段、当前图片和未关闭差异，再继续；不得跳过实际看图步骤。

### 19.3 对当前塔／机甲的重点

检查头肩比例、装甲主平面朝向、躯干／腿比例、装甲厚薄层级、关节间隙、背部结构、负空间和机械连接。用户批准的是具体概念，不是“像个机甲”这一大类。

建模结果若变成软塌的一体外壳，应检查截面与主平面并分件重做关键硬表面，不用一层金属材质掩盖。复杂曲面可以采用细分、雕刻或经授权复用的合适底模，不要求所有曲面手写坐标。

### 19.4 进度记录

长任务在本地保存 `implementation_status.json` 和简明中文日志，按能力／测试而非虚构百分比报告。上下文恢复后读取这些文件，不重复覆盖已经完成的部件。

可以记录运行时间、资源峰值和缓存命中帮助诊断，不做用户明确不需要的云费用统计和 API 额度管理。

## 20. 真实验收任务

全部验收属于同一次升级。小型确定性样例用于验证算法和边界，真实项目参考用于验证制作价值，两者必须都有，不能互相冒充。

### 20.1 A-01：Blender 原生视觉闭环建模

在未配置图生 3D 后端和模型权重的环境中，输入来源明确、姿态一致的 front／left／back 图片。可以用带不对称标识的自建机械校准件制作参考；其源几何只用于生成参考和独立比对，不得直接复制为新候选。

Codex 实际读取图片，记录部件、轮廓、截面及推断区域，通过 Blender 原生操作从新候选建立有真实三维体积的可编辑模型。保留计划、实际操作、参数、对象映射与输出哈希，展示灰模和线框。

至少完成一轮有实质意义的“出图 → 实际识别差异 → 局部修改 → 再出图并复核”：例如纠正肩甲宽度或胸甲侧向厚度，同时证明头部与非目标部位保持。若初始测试件没有可修差异，可以明确注入可追踪的受控几何偏差用于测试，不能伪称自然出现的错误。

对比使用相同相机、姿态、尺度和显示条件，包含正侧背及一个未直接提供参考的三分之四检查视角。后者用于检查立体结构，不冒称未知视角已经得到用户批准。

通过条件包括：原生几何真实创建、实际图片被审阅、差异关联正确版本、局部修正改善目标问题、保护区检查通过、新图复核完成、闭环阶段和可编辑产物可重新读取。一次脚本执行、单次截图或自动指标达标都不足以通过 A-01。

### 20.2 A-02：当前已批准机甲参考的造型改进

从第 2.3 节路径和最新项目记录读取批准概念。优先选择头部—胸甲—肩甲代表性结构作为升级验收资产；实际确认已有批准的范围，不自动扩展到未批准全身设计。

保留旧 R2／R3。创建新候选，提交相同视角的批准参考、旧失败候选和新候选对照。重点说明哪些比例、厚度、转折、间隙和连接获得实质改善，哪些仍有差距。

不允许只交文字“更接近”。至少给出一项具体局部修改的操作记录、修改前后图片和受保护部件未变的验证。

如项目只提供单视角，这一项仍可验证可见部分与局部修形；A-01 另行验证多视图对齐与原生建模闭环，不能把推断侧背图算作用户批准参考。

### 20.3 A-03：可控硬表面建模

制作一个包含自定义轮廓、多个截面、装甲厚度、凹槽、独立连接／转轴和局部修正的代表塔或机械部件。

必须展示 recipe 和可编辑参数；改动肩宽、板厚或底座截面后，结构能够有控制地更新。仅布尔切几个洞的基础立方体不能作为全部硬表面能力证据。

测试资产没有用户批准参考时，明确标为工程测试件，不写成 ShooterRoyal 已批准生产塔。

### 20.4 A-04：游戏资产和动作

对达到当前视觉自评标准的候选，完成 UV、材质、必要的高低模烘焙、刚性绑定／柔性权重、pose suite、导出和独立读回。

展示实际贴图图像、材质预览、线框、关节动作与回姿态；检查高低模角色、方向、世界尺寸和纹理依赖。

对真实机械资产不强制多余的人体布线，但要用单独的关节测试件验证柔性权重工具，不能因为机甲主要刚性就不实现所要求的权重编辑能力。

### 20.5 A-05：恢复和重新进入任务

在一次有意义的局部编辑前创建检查点，执行修改并保存图像，再恢复到新候选，确认几何、部件和关键参数回到对应状态。旧 session／selection 必须失效。

让一个自有后台 Blender 渲染或烘焙任务在受控条件下中断，验证真实状态和重新查询；另验证闭环在待审阅阶段中断后能恢复未关闭差异及当前证据。恢复后不重复提交旧写入、不把半成品注册为成功、不触碰用户原有实例。

### 20.6 A-06：安装态和 MCP 实测

从实际安装路径加载 Blender 插件，通过真实 MCP 客户端完成 initialize、工具枚举、实时 catalog、原生建模操作、一个自有后台 Blender 任务、实际图片返回，以及审阅登记和闭环继续操作。

测试服务重连和客户端工具目录未刷新时的 CLI 诊断路径。核对已安装源码和本次构建一致，其他 MCP 配置未变化。

### 20.7 验收结果要求

每项返回 `passed`／`failed`／`blocked`／`not_run` 和明确证据。需要人工审美的项目使用 `self_review_passed` 与 `pending_user_review`，不把人工项塞进机器 PASS。

A-01 原生视觉闭环不能以 `skipped` 或缺少图生 3D 模型为由绕过后整体通过。A-02 缺参考时记录阻塞并先完成其他测试；最终报告不能写“全部完成”，但应完整交付已完成代码和可用产物，不只留下方案。图生 3D 扩展不属于本次验收集合，不计为缺失、阻塞或待补功能。

UE 现场没有授权时，仅 UE 验证项可以保持 `not_run`，不要求为了工具升级越权导入。

### 21.3 数值容差和不确定性

几何算法测试应根据单位和样例设明确容差，支持确定性复现。跨 Blender 版本或 CPU／GPU 渲染设备不要求图片哈希相同；记录版本、参数、实际使用的随机种子及适合的几何／图像比较结果。

`not_checked`、`unknown`、`not_applicable`、`failed` 不能混写。验收摘要同时报告真实运行、未运行和阻塞数量，不只显示“通过率 100%”而隐藏未测项目。

### 21.4 性能与上下文负担
